## 1. アーキテクチャ概要

本ツールは、**SVG IR**（SVGのサブセットとして定義する内部中間表現）を中核に置く。
取得側（フロントエンド）と出力側（バックエンド）はSVG IRだけを介して接続し、互いの実装を知らない。

```
[PETA: 全体・窓（選択絞り込み可）] CAD PDF印刷 ─→ PDF解析 ─┐
                                                ├─→ SVG IR ─→ IR変換層 ─→ SVG/EMF
[PETADATA: 選択] CAD DB直接取得 ────────────────┘
                                          ┌──────────┬──────────┼──────────┐
                                        EMF出力    SVG出力    PDF出力    PNG出力
                                          │
                                   クリップボード / ファイル
```

この分離が満たす性質は三つある。
取得系統を追加しても出力側に手が入らない（互換CAD対応の追加費用が下がる）。
出力形式を追加しても取得側に手が入らない（EMF一本足を避ける）。
不具合の切り分け点がIRという一つの観測面に集約される（IRを見れば取得と出力のどちらの問題か判定できる）。

### 1.1 依存規則（Clean Architecture）

本ツールの実装は Clean Architecture に従う。参照（依存）の方向は外側から内側への
一方向のみとし、逆流を認めない。

- **内核（ドメイン層）**: SVG IR モデルと IR 変換層（整形・色変換）。
  外部ライブラリへの参照を持たない（PdfPig・AutoCAD .NET・GDI の型がここに現れてはならない）
- **ユースケース層**: 取得→変換→出力のオーケストレーション。
  境界ポート（取得ポート・出力ポート等の interface）を所有する
- **アダプタ層（外側）**: PETADATA用CAD DB取得／PETA用CAD印刷とPdfPig／EMF（GDI P/Invoke）／
  SVG／クリップボード／UI。内側のポートを実装し、依存性注入で結線する

参照方向は .NET のプロジェクト分割で物理的に強制する（ドメインプロジェクトは
パッケージ参照ゼロを維持する）。§1 の「取得側と出力側は SVG IR だけを介して接続し、
互いの実装を知らない」という原則は、この依存規則の帰結として保証される。

## 2. SVG IR 制約プロファイル

SVG IRは任意のSVGではなく、以下に許可要素を限定した制約プロファイルである。
出力バックエンドが処理すべき対象を有界にすることが目的であり、プロファイル外の要素はIRに存在しない。

### 2.1 許可要素と属性

| 要素 | 用途 | 主な属性 |
|---|---|---|
| `path` | 線分、円弧、ベジェ曲線、ハッチ輪郭 | `d`, `stroke`, `stroke-width`, `fill`, `fill-rule` |
| `polyline` / `polygon` | 折れ線、閉多角形 | `points`, `stroke`, `stroke-width`, `fill` |
| `text` | 文字（フォント保持の場合） | `x`, `y`, `font-family`, `font-size`, `transform` |
| `image` | 図面内ラスタ画像の位置保持 | `x`, `y`, `width`, `height`, `href`（埋め込み） |
| `g` | レイヤ・ブロック単位のグループ | `id`, `transform`, `clip-path` |
| `clipPath` | ビューポート境界、ワイプアウト | `path`または`polygon`を子に持つ |

線種（破線）は`stroke-dasharray`と`stroke-dashoffset`で表現する。
PETADATAのDB取得では、CADの実描画が行う破線パターンの端部整列
（開いた曲線=両端が実線片で始終するよう位相・端片を調整、
閉じた曲線=パターンを整数周期へ伸長）を再現して生成する
（アルゴリズムは実測で導出。根拠は docs/validation/architecture-decisions.md）。
透明度は`stroke-opacity` / `fill-opacity`としてIRに保持し、劣化の判断は出力バックエンドに委ねる（第6章）。
グラデーション、フィルタ、アニメーション、スクリプトは許可しない。

生成規約: `clip-path`は`transform`を持つ要素に直接付与しない（SVGではクリップ幾何が
要素自身のtransformで変換されるため）。この場合はクリップを親`g`に置く
（実測根拠は docs/validation/architecture-decisions.md §4）。

生成規約: グリフ位置列を明示する`text`で先頭空白または連続空白を含む場合、
`xml:space="preserve"`と`style="white-space:pre"`を要素に直接付す（SVGの空白正規化で
位置列と文字数がずれるため。ルート要素への指定はChromeでは効かない。
実測根拠は docs/validation/architecture-decisions.md §4.2）。

生成規約: レイヤ別グループ化（§5.1）が生成する`g`には、`id`（レイヤ初出順の連番）に加え、
SVG エディタがレイヤとして認識する規約属性 `inkscape:groupmode="layer"` と
`inkscape:label`（レイヤ名）を付す（エディタのレイヤパネルに出すことが本機能の目的のため）。
名前空間宣言（`xmlns:inkscape`）はこのグループ化の適用時だけ出力し、未適用の出力は従来と
バイト不変。他レンダラは未知属性を無視する（Chrome・Inkscape で実測済み。
実測根拠は docs/validation/architecture-decisions.md）。

### 2.2 座標系と単位

- ルートの`viewBox`は図形範囲（クロップ後）を表す
- `width` / `height`はmm単位の物理寸法を持ち、貼り付け時の実寸再現（FR-6）の根拠となる
- Y軸はSVG標準（下向き正）とし、CAD座標（上向き正）からの反転は取得側の責務とする

### 2.3 出所メタデータ

PETADATAでDB取得した要素は、元データの属性をカスタムデータ属性として保持する。

| 属性 | 内容 |
|---|---|
| `data-color-method` | `aci` / `truecolor` / `bylayer` / `byblock`（解決前の指定方法） |
| `data-aci` | ACI番号（1〜255。ByLayer/ByBlockは解決後の値を記録） |
| `data-layer` | 元レイヤ名 |
| `data-entity` | 元エンティティ種別（診断用） |

このメタデータは診断出力での標示とレイヤ別グループ化（§5.1）が参照する。
PETAまたはCLIのPDFから取得した要素は data-layer（レイヤ情報付きPDFの場合）以外のメタデータを持たず、
変換層は該当する処理を自動的に不能と判定する。
系統間の機能差を、分岐コードではなくメタデータの有無として表現する。

## 3. PETADATA（構造SVG用DB直接取得）

### 3.1 構成

PETADATAはCAD内で動作する独立コマンドとして実装する。PETAの貼付経路からは参照しない。
プラグインはCADのAPIを**取得アダプタ**という共通インターフェースの背後に隠蔽し、CAD製品ごとの差異をアダプタ実装に閉じ込める。

- AutoCAD：.NET API（本線）
- BricsCAD：.NET API（AutoCAD .NETとの高い互換性を利用する）
- IJCAD / ARES等：各社API。対応可否と方式はアダプタ単位で個別判断する

ARESは版でSDKアセンブリ名とホストランタイムが異なる（2020／2023／2024＝.NET Framework 4.8、2027＝.NET 8）。
アダプタとプラグインはこの差を、net48ターゲット内の年式選択（`AresSdkYearNet48`）と2027向けnet8ターゲットで吸収する。
名前空間は全世代で共通のため、コードは版差を持たない。
版ごとのSDKアセンブリ名の対応は `src/Directory.Build.props` の表が一元管理する。

### 3.2 エンティティからIRへの対応

| CADエンティティ | IR表現 |
|---|---|
| 線分、ポリライン | `polyline` / `path` |
| 円、円弧、楕円 | `path`（楕円弧コマンド） |
| スプライン | `path`（3次非有理クランプはノット挿入による厳密ベジェ変換。それ以外は許容誤差〔既定 0.01mm〕の折れ線近似とし、処理ログに記録する） |
| 文字（TrueType） | `text` |
| 文字（SHX） | `path`（輪郭化。ストロークフォントのため線として展開する）。設定で代替書体の`text`へ切り替えられる（貼り付け先での文字編集を優先する場合。代替の事実は処理ログに記録する） |
| ハッチ | `path`（塗りまたはパターン線の展開） |
| ワイプアウト | 背景色`polygon`（白塗り）。`clipPath`表現は採らない（Officeの「図形に変換」がクリップを破棄する実測による） |
| ブロック参照 | `g`（変換行列付き）に展開 |
| 寸法 | 構成要素（線、矢印、文字）へ分解して上記に帰着 |
| 複雑線種の記号（シェイプ・文字） | 記号をSHX解釈でジオメトリ（`path`）へ展開する（破線パターン自体は`stroke-dasharray`のまま、端部整列後の位置へ破線と一体で調整する）。展開は処理ログに記録する |

### 3.3 色の解決

ByLayer / ByBlockの色は取得時に実効値へ解決し、解決前の指定方法を`data-color-method`に記録する。
ACIとTrueColorの区別はCADのAPIが提供する色オブジェクトの種別判定に基づき、推測を含まない。

## 4. PETA（PDF印刷単一経路）

### 4.1 範囲プロットと選択絞り込み

**範囲（全体・窓）**：CAD内のPETAから、対象レイアウトをベクタPDFへサイレントプロットし、生成PDFを続けて処理する。
利用者から見れば一操作で完結する。
この経路はAutoCAD、ARES Standard 2020／2023／2024／2027、IJCAD 2026 PRO、BricsCAD V26で実装する。
実機E2EはAutoCADとARES 2024／2027、IJCAD 2026 PRO、BricsCAD V26で確認済みである。
ARES 2020／2023の実機状況は `docs/validation/compatible-cad.md` に記録する。
製品固有のプロットAPI・PDFデバイス名・用紙寸法取得は `IPlotPort` 実装へ閉じ込め、範囲判断と窓配置計算は4製品共通とする。
窓はプロット領域（Window）に設定して発行し、縦横比差の余白帯は変換層のクロップで切る。

**選択絞り込み**：オブジェクト選択（先選択またはオブジェクト(O)）は、確定した範囲の中で出力対象を選択オブジェクトだけに絞る。
モデル空間の選択図形はWblockで側DBへ複製する。
通常のペーパー空間図形は図面全体のWblockで依存データを保持した側DBを作り、選択図形を元レイアウトへ一括複製してから非選択図形を消去する。
OLEは`Position3d`の四隅から安定した範囲を求め、`IdMapping`の一次複製、所有BTR、実行時型、複製先IDの一意性によって選択実体の欠落と取り違えを検出する。
通常ビューポートを含むペーパー空間選択は、側DBでは表示内容を再現できないため、元図面の未確定トランザクション内で非選択のペーパー空間図形だけを一時的に非表示にする。
選択ビューポート、非矩形クリップ境界、モデル空間、ビューポートのOn状態、尺度、視点、固有の画層状態と画層overrideは保持したまま元レイアウトを印刷する。
同時選択された非印刷レイヤの紙図形は、ビューポート以外に限って未確定トランザクション内の一時退避レイヤへ移し、元レイヤに属するビューポート内のモデル図形へ影響させない。
終了時にトランザクションを破棄し、一時変更した図形の可視状態とレイヤ、一時レイヤの消滅を直接検査する。
範囲の種別・尺度採否・窓クロップ矩形の判断は、絞り込みの有無に依らず同じ範囲プロット実装が担う。
モデル空間源では元図面のアクティブビュー（視線方向とねじれ）も側DBへ複製し、窓の座標系を一致させる。
Defpoints等は一時側DBまたは元図面の未確定トランザクション内で、印刷可能な退避レイヤへ移す。
Viewportの選択可否は、制御Viewportを番号、表示内容のないオフViewportを`On`で判定する。
`Number == -1`は画面外または`MAXACTVP`超過による非アクティブ状態も表すため、`On`であれば通常Viewportとして出力する。
同様に、番号未割当を表し得る`Number == 0`もオフの代用には使わず、`On`であれば出力する。
Xref、別空間の図形、ペーパー空間の制御ビューポート、オフのビューポートは非対応として確認する。
Wblockが失敗または空の側DBを生むときはオブジェクト複製（WblockCloneObjects）へフォールバックする。このフォールバックの側DBは既定のCTBモードで作られるため、STB図面ではモード不一致として中止する（既知の制限）。元図面、BACKGROUNDPLOT、WorkingDatabaseは必ず復元する。

**CLI/GUI入口**：既存のベクタPDFファイルを直接受け付ける（FR-7）。
CADのインストールを前提とせず、プラグイン未対応のCADからの受け皿となる。

### 4.2 PDF解析からIRへ

PDF内容ストリームからパス、テキスト、クリップ、画像を取り出し、IRへ写像する。
座標系はPDFのポイント単位からmm基準へ正規化する。
プロットスタイルはPDF生成時点で適用済みのため、色は最終RGB値としてそのまま保持する。

写像規則は docs/validation/architecture-decisions.md §3（テストチャートで確定）、
docs/validation/architecture-decisions.md §4（実物図面で追加）および
docs/validation/architecture-decisions.md §5（回転ページで追加）で実測確定したものを基準とする。要点:

- パスはベジェ制御点を保持し、色は最終RGB、線幅はCTMスケール補正後のmm値とする
- 文字はテキスト表示オペレータ単位のランとし、グリフごとの位置列で字送りを固定する。
  幅係数（Tz）は`scale`、回転はベースライン方向から求めた`rotate`で`transform`に写す
- 線幅0（デバイス最細線）はSVGに対応概念がないため固定幅へ置換し、診断ログに記録する
- レイヤ（OCG）は要素単位の`data-layer`に写す（z順保存と両立させるため`g`を使わない）
- 描画順は内容ストリーム順を保存する（ワイプアウト=白塗りの成立条件）
- 回転ページ（/Rotate 90/180/270）はパス・文字が表示座標系で得られる一方、画像境界は
  回転矩形で得られるため、四隅から軸平行bboxを取り四半回転を画素へ無劣化で焼き込む
  （非直角回転は近似配置＋診断ログ）

### 4.3 背景矩形の同定

プロット出力のPDFは、用紙全面を覆う塗り矩形を先頭付近に持つことが多い。
「描画順が最初期」「ページ範囲とほぼ一致」「塗りのみ」の三条件で背景候補を同定し、既定で除去する。
誤除去に備え、除去の無効化と、除去対象の診断表示（IRダンプ内での標示）を提供する。

実測（AutoCAD PDF (High Quality Print).pc3、テストチャート2種・実物4種）では背景矩形は
出現しなかった。三条件判定は、他ドライバ・他CAD由来のPDF（FR-7）への防御として維持する
（実測根拠は docs/validation/architecture-decisions.md §3）。

### 4.4 用紙の対応付けと代替用紙

PETAはページ設定のデバイスだけをPDFデバイスへ上書きするため、用紙の正式名（CanonicalMediaName）はデバイス固有の名前空間となり、元の名前が上書き後のデバイスに存在することを期待できない。
そこで用紙は名前ではなく公称寸法で対応付け、同名の用紙があっても寸法が一致するときだけ同一用紙として採用する。
名前だけの一致を根拠にすると、別デバイスの同名別寸法用紙を黙って使い、出力寸法とページ設定の尺度の意味を壊すためである。

寸法の合う用紙がPDFデバイスに無い場合は、処理を中止せず既定の代替用紙で完遂する。
既定はISO A4縦（210×297mm）とし、環境変数 `CADPETA_FALLBACK_PAPER_MM`（`幅mm,高さmm`）で上書きできる。
不正な構成値は黙って無視せず失敗として顕在化する。
代替用紙の実体は、構成寸法を収容する最小の実在用紙、収容できる用紙が無ければ最大の実在用紙を、候補の列挙順や端末の既定用紙に依存しない決定規則で選ぶ。
選択した用紙の縦横が構成寸法と食い違う場合は90度回転で正規化し、範囲はExtents、尺度はFit、中央配置として意味を保つ。

この代替は発行用の一時ページ設定（`PlotSettings` コピーと `PlotInfo.OverrideSettings`）だけに適用し、図面のページ設定は変更しない。
用紙の読み替えと代替への縮退は、いずれも件数と対象をログ・診断へ残す（第7章）。

## 5. IR変換層

IR変換層は、IRを受け取りIRを返す変換の直列合成である。
変換の適用順は固定とし、以下の順で通す。

1. **背景除去**（PDF由来IRのみ対象）
2. **クロップ**：全体・窓は指定矩形、選択は取得内容のbboxを再計算して余白を付与
3. **線幅正規化**：最小線幅の保証
4. **色変換**：モノクロ化、グレースケール化、色の一括置換（仕上げ変換として扱う）
5. **レイヤ別グループ化**：`data-layer` によるレイヤ初出順の `<g>` 再グループ（既定オフ。構造変換のため最後に適用する）

### 5.1 レイヤ別グループ化

FR-4 のレイヤ別グループ化は、`data-layer` を持つ要素をレイヤ初出順の `<g>` へ再グループする
IR 変換である。z順（描画順）の保存と両立しないため既定オフとし、適用時はレイヤ数と移動要素数を
処理ログへ記録する（第7章）。実物図面で描画順の入れ替えによる見た目の崩れが起きることを
実測済みである（docs/validation/architecture-decisions.md §3.1）。`data-layer` はPETADATAとレイヤ情報付き
印刷PDFの双方が持ち得るため、この変換は入口に依存しない。

## 6. 出力バックエンド

### 6.1 EMF出力

Office貼り付け時の編集忠実度を最優先し、クラシックGDIレコード（EMF+ではない）の生成を第一候補とする。
この選択は実測で確定した（要求仕様書§8、docs/validation/architecture-decisions.md §5）。

- ヘッダの`rclBounds` / `rclFrame`に、IRの物理寸法から算出した値を設定し、貼り付け時の実寸（FR-6）を実現する。
  Officeの貼り付けサイズは「rclFrame × ヘッダszlDevice/szlMillimeters比 ÷ 96dpi」で算出され、
  記録デバイスの実解像度を無視して96dpiを仮定することを実測で確認した（実画面108.9dpiの
  参照DCでは+13.5%で貼り付く）。このためEMFの記録は論理単位0.01mmのMM_ANISOTROPICとし、
  デバイス解像度をviewportとヘッダszlの両方で96dpi固定として書く（docs/validation/architecture-decisions.md §4）。
  この96dpi仮定は表示スケール（論理DPI 96/120/144）に依存しないハードコードであることを実測で確認した（docs/validation/architecture-decisions.md）
- 透明度を持つ要素は、不透明色への近似（白背景との合成）へ劣化させる。劣化した事実を処理ログに記録する
- 図面内ラスタ画像（`image`要素）はSTRETCHDIBITSの無圧縮DIBで出力する。透明度は上記のとおり白背景と事前合成して不透明化済みのため、DIBは**24bpp BGR**（未使用のアルファバイトを持たない）とし、画素を無損失に保ったままOLE由来画像等のEMF肥大を抑える（32bpp比で約25%減。行はDWORD境界へパディングする。docs/validation/architecture-decisions.md §8、docs/validation/architecture-decisions.md）
- 文字は、TrueTypeフォント保持（`text`要素をフォント付き文字レコードへ）と輪郭化の二方式を設定で選べる。フォント保持は貼り付け先での編集性に優れ、輪郭化は環境非依存の見た目を保証する
- クリップ（`clipPath`）はEMFのクリップレコード（EXTSELECTCLIPRGN等）として出力しない。Officeの「図形に変換」がクリップ状態を破棄することを実測で確認したため（docs/validation/architecture-decisions.md §4.5）、IRの`clipPath`はEMF生成時にジオメトリへ適用（事前クリップ）してから出力する。文字と交差するクリップは輪郭化を要するため、非可逆処理として処理ログに記録する（第7章）
- Officeの「図形に変換」は現在位置依存のレコードを正しく処理せず、線の終点が飛んで図形が崩壊することを実測で確認した（docs/validation/architecture-decisions.md §6）。このためパスブラケット外の描画は始点込み絶対座標レコード（POLYLINE16/POLYBEZIER16等）のみで書き、MOVETOEX＋"To"系レコードおよびSETWINDOWORGEXによる原点移動は使わない
- 「図形に変換」による分解編集の主対象はExcel / PowerPointとする。WordはEMFの分解編集を積極サポートしない。既定の貼り付け先である描画キャンバス内ではグループ解除が使えず、直接挿入での分解も動作が不安定（互換モード様の選択ハンドル、Undoでのオブジェクト二重化）なことをGUI確認で観測したためである。Wordでは実寸画像としての貼り付けを主用途とする

### 6.2 SVG出力

IRはSVGの制約プロファイルであるため、出力はほぼ直列化のみとなる。
透明度を含む全属性を無劣化で保持する。
出所メタデータ（`data-*`）は既定で除去し、診断用出力でのみ残す。

### 6.3 PDF出力・PNG出力

PDF出力は単票の受け渡し用、PNG出力は表示互換の確認用として、IRの描画結果を書き出す。
両者はEMF/SVGに対する従属的な出口であり、初版では最小限の実装にとどめる。

### 6.4 クリップボード

EMF出力を`CF_ENHMETAFILE`形式でクリップボードへ登録する。
SVGにはOffice間で通用する標準クリップボード形式がないため、SVGはファイル出力のみとする。

### 6.5 成果物の公開と検証

出力ファイル（PDF・SVG・EMF・PNG）は、公開先と同じディレクトリの一時ファイルへ書き、形式検証を通過した後に原子的置換で公開する。
書込途中の異常終了や検証失敗では既存の成果物を変更しない。
0バイトや途中書きのファイルが成果物として残ると、後段のOffice貼付や再利用が黙って壊れるためである。

形式検証は各形式の構造を終端まで確かめる。
PDFはヘッダー・`startxref`の指示範囲・`%%EOF`、EMFは全レコード走査と宣言長・EOFレコード、SVGはXMLの完結とルート要素、PNGはチャンク列の完結（IHDR・IDAT・IEND）を検査する。
CADのプロットが生成するPDF、クリップボード代替として保全・回収するEMFにも同じ検証を通し、検証を通らないファイルを利用可能な成果物として案内しない。

## 7. 診断設計

NFR-3（診断可能性）を、IRの観測面としての性質で実現する。

- 変換層の各段の前後で、IRをSVGファイルとしてダンプできる（診断モード）
- ダンプはそのままブラウザで開けるため、専用ビューアを要しない
- 背景除去の対象、透明度の劣化、SHX輪郭化といった非可逆処理は、診断モード（PETADIAG / CLI `--diag`）で件数と対象を `.diag.json` に記録する。通常実行は簡潔な結果サマリのみを示す。各段SVGダンプも診断モードだけが生成する

不具合報告に対し、IRダンプの提出だけで「取得・変換・出力のどこで壊れたか」を切り分けられる状態を目標とする。

## 8. 技術選定と実行基盤

実装言語は C#（.NET）とする。PDF解析は PdfPig を本実装に採用し、pypdfium2（正解レンダラ）・
pikepdf（解剖）・PDFBox（正解データ生成器）を検証補助に用いる。根拠は
docs/validation/architecture-decisions.md。

実行基盤: 開発・単独配布（CLI・単独入口）は .NET 10 を基本とする。プラグインはホスト AutoCAD の
ランタイム（2024 以前 = .NET Framework 4.8、2025/2026 = .NET 8、2027 = .NET 10）で読み込まれる
ため、内核は netstandard2.0、プラグイン側アダプタは3系マルチターゲットとする。TFM（Target
Framework Moniker: .NET のターゲットフレームワーク識別子。net48 / net8.0-windows /
net10.0-windows）の割当てと根拠は src/Directory.Build.props に一元定義する。

## 9. リスクと対応

| リスク | 対応 |
|---|---|
| PDF解析でベクタが素直に取れない図面がある（複雑なハッチ、透過PDF設定等） | Phase 0で実物図面のコーパスを作り、取れない類型を早期に特定する。プロット設定側の推奨値（透過なし等）を利用者向けに文書化する |
| クラシックEMF生成の実装コストが想定を超える | EMF+へ一時後退し、編集忠実度の劣化を明記して初版を出す。IR中心設計のため、後からEMFバックエンドのみ差し替えられる |
| 互換CADのAPI差異がアダプタで吸収しきれない | 該当CADプラグインを明示的に非対応とし、CLI/GUIのPDF入力を後退経路にする。貼付経路をDB直接取得へ戻さない |
| OfficeのEMF受け入れ方針の変更 | SVG出口が既に存在するため、既定出力の切り替えで追随できる |

## 10. グラデーションハッチとEMF背景色

PETADATAではグラデーションハッチを取得時にアルファ付き`IrImage`へ正規化し、SVGのgradient要素は
IR制約へ追加しない。対応形状はLINEAR、CYLINDER、INVCYLINDER、SPHERICAL、
INVSPHERICAL、HEMISPHERICAL、INVHEMISPHERICAL、CURVED、INVCURVEDの9種である。

- 色、角度、Shift、OneColor/TwoColorは各CADの公開Gradient APIから取得する。
- 空間式と画素中心規則はAutoCAD純正プロット29枚から固定し、全9形状をゴールデンテストする。
- 境界は画像アルファへ焼き込む。回転・鏡像・非等方・入れ子ブロックは、文書座標との可逆行列で評価する。
- 既定150dpi。名前付きの辺長・1画像画素数・文書総画素数上限から実DPIを決める。
- 未知形状、特異変換、予算不足だけを代表色へ縮退し、対象と理由を診断へ残す。
- 純計算とPNG生成はCAD SDK非依存の`CadPeta.Acquire.Raster`へ集約する。

EMFは真のアルファを保持しないため、path、text、imageを既定白または指定`#RRGGBB`背景と
同じ規則で事前合成する。既定白は従来出力とバイト一致する。式、許容差、4製品APIの根拠は
`docs/validation/gradient-rasterization.md`、正解コーパスは`tests/assets/testcharts/gradient/`を基準とする。

## 11. 表示文言の多言語化（lang ファイル）

プラグイン（PETA / PETADATA 系）のコマンドライン表示文言は、言語カタログから引いて日本語と
英語で出し分ける。対応言語は ja / en の2言語とし、未対応言語は英語で表示する。
CLI・GUI の文言は現状この対象に含めず日本語のままとする（lang ファイル自体は4種の配布物
すべてへ収録する）。

- カタログは LCID 名の平文ファイル `1041.lang`（日本語）/ `1033.lang`（英語）で、プラグイン DLL の
  隣の lang フォルダへ配備して実行時に読む。文言の差し替え・言語の追加は lang ファイルの編集・
  追加で済み、再ビルドを要しない。同じ内容を組み込みリソースにも持ち、lang フォルダのファイルが
  無い・読めない場合は組み込み側で動作を続ける
- どのファイルを使うかはホスト言語の二文字ファミリで決める（LCID の完全一致にしない）。
  ja 系は 1041.lang、en 系は 1033.lang、それ以外と判定不能は 1033.lang とする。判定不能・
  ファイル欠落・キー欠落は黙って倒さず、その旨をコマンドラインへ報告する
- 翻訳するのは表示文言だけとする。コマンド名（PETA 等）、キーワードのグローバル名
  （All / Object 等）、診断カテゴリ文字列と diag.json の内容、確認プロンプトの応答（Y / Yes）は
  言語に依らず不変とし、スクリプト・自動化・機械比較が言語で割れないようにする
- 例外メッセージ等に内挿される下位層・BCL・CAD API の文（ex.Message、ErrorStatus 等）は
  実行環境の原文のまま残し、説明の枠だけを翻訳する
- カタログの読込は BCL の範囲で行い、外部パッケージを追加しない（CadPeta.Core の外部参照ゼロは
  不変）

# PDF GUIの構成

`CadPeta.Core`（IR・値オブジェクト）→ `CadPeta.UseCases`（変換ユースケース）→
`CadPeta.App`（PDF取得と出力アダプタを結線するApplication層）→ `CadPeta.Cli` / `CadPeta.Gui`
（Presentation層）の方向とする。GUIとCLIは互いを参照せず、CAD SDKはこの経路へ入れない。

`PdfPetaPipeline` が取得、固定順変換、全形式出力、診断集約を一度だけ実装する。CLIの段階診断はI/Oを行う
診断シンクをRunOptionsで注入する。GUI固有の入力・保存先検証は共通不変条件と分け、CLI互換性を保つ。
GUIの一時成果物は起動セッション別ディレクトリと排他ロックで所有し、使用中の別プロセスを清掃しない。
